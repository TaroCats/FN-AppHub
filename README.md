# AppHub 应用聚合中心（飞牛 fnOS 原生应用）

把本机所有 Docker 应用的 Web 入口聚合成一个页面，自动扫描容器暴露端口，支持在应用内直接内嵌浏览。

- 当前版本：1.0.29
- 安装包：`apphub_1.0.29.fpk`（飞牛应用中心 / FnDepot 均可安装）
- 端口：9080（host 网络）
- 数据目录：`/var/apps/apphub/shares/apphub/data`（SQLite 数据库 `apphub.db`）

## 安装

### 方式一：FnDepot 第三方源（可自动更新）

1. 打开 FnDepot → 设置 → 外部应用源 → 添加源。
2. 填入仓库地址：

   ```text
   https://github.com/TaroCats/FN-AppHub
   ```

3. 同步后即可在 FnDepot 中看到「应用聚合中心」，后续新版本会直接提示升级（直接安装 fpk，数据保留）。

源索引是仓库根目录的 [`fnpack.json`](fnpack.json)，遵循 FnDepot 外部应用源 V2 规范（`schema_version: "2"`），FPK 从 GitHub Release 下载并带 `sha256` 与 `size` 校验。
如果客户端版本较旧、无法识别仓库地址，也可以直接添加 JSON 直链：

```text
https://raw.githubusercontent.com/TaroCats/FN-AppHub/main/fnpack.json
```

### 方式二：手动安装

1. 从 [Releases](https://github.com/TaroCats/FN-AppHub/releases) 下载最新的 `apphub_x.y.z.fpk`。
2. 飞牛桌面 → 应用中心 → 右上角「…」→ 手动安装应用（或直接双击 fpk）。
3. 安装过程直接从 GHCR 拉取预构建镜像（`ghcr.io/tarocats/apphub`），本机不再执行 `docker build`，安装只需下载镜像层，速度取决于网络。
4. 桌面出现「应用聚合中心」图标，点击后在飞牛桌面窗口内加载。

> 升级：直接安装新版本 fpk 覆盖升级，访问列表保留在 `/var/apps/apphub/shares/apphub/data/apphub.db`。
> 若安装后图标点击无反应，检查 9080 是否被占用：`ss -lntp | grep 9080`。
>
> **镜像仓库必须公开**：安装端不做 `docker login`。若 GHCR 包被设为私有，会报 `pull access denied`——到 GitHub → Packages → `apphub` → Package settings 里把可见性改为 Public（首包发布后默认继承仓库可见性，需手工确认一次）。

## 功能

| 功能 | 说明 |
| --- | --- |
| 自动扫描 | 读取 `/var/run/docker.sock`，列出所有运行中容器的对外端口，自动挑选最像 Web 的端口（80/443/8080/3000/5244 等优先），默认过滤 80/443 与内部服务 |
| 批量导入 | 扫描抽屉里勾选多个容器，一键加入访问列表；已收录的标记「已添加」 |
| 手动新增 | 名称、地址、端口、协议、分组、图标，支持任意内网/外网 URL |
| 访问列表管理 | 编辑、删除、分组、搜索（按名称/地址/分组） |
| 应用内浏览 | 每个条目可在 AppHub 窗口内浏览，也可新标签页打开；内嵌一律使用应用自己的 IP:端口，不经过任何代理 |
| 多窗口浏览 | 同时打开多个应用，顶部标签切换；默认全屏，可切分屏（零间隔平铺、拖交界处调宽高）与缩小（可拖动、可缩放的浮动窗） |
| IP 直连 | 应用地址统一保存为 `http://<局域网IP>:端口`，浏览器直接访问：不用域名、不用 hosts、不经过反向代理 |
| 在线状态 | 后台定时探测目标可达性，卡片上显示在线/离线 |
| 图标抓取 | 自动尝试抓取目标站点 favicon，失败则用首字母色块 |

## 构建与发布（GitHub Actions）

工作流：[`.github/workflows/build-fpk.yml`](.github/workflows/build-fpk.yml)

| 触发方式 | 行为 |
| --- | --- |
| push 到 `main` / Pull Request | 用官方 `fnpack` 打包并校验包内 manifest，仅上传 workflow artifact，不发布 |
| push 标签 `v*` / 手动 `workflow_dispatch` | 构建镜像并推送到 `ghcr.io/tarocats/apphub`（版本 tag + `latest`）→ 校验镜像可匿名拉取 → 打包 fpk → 创建/更新 Release → 重写 `fnpack.json` 版本节点 → 回写 `main` |
| 手动 `workflow_dispatch` | 可选 `none/patch/minor/major` 递增版本号，随后与 tag 发布流程一致 |

### 镜像构建与分发

镜像在 CI 里构建，安装端只拉取，这是「更新失败」类问题的根治方式：

- **不再现场打包**：容器镜像 `ghcr.io/tarocats/apphub` 由 `docker/build-push-action` 在 GitHub Actions 上构建并推送，设备端不再执行 `docker build`。以前每次安装/升级都要在 NAS 上重新构建，既慢，又在构建失败时把整个更新卡死。
- **不再有本地 `<app>:<ver>` 镜像**：旧 compose 写 `image: apphub:1.0.26` 且带 `build:`，docker 会先去仓库找一个叫 `apphub` 的镜像，找不到就报 `pull access denied for apphub, repository does not exist`——这正是更新报错里最容易被误读的一条。现在 compose 只指向 GHCR，不存在这个名字冲突。
- **升会强制拉新**：`upgrade_init` 会先 `docker image rm` 本地同名 tag 再 `docker pull`，避免 docker 认为"已是最新"而跳过，升级后跑的还是旧镜像。
- **compose 写了 `name: apphub`**：旧版没有项目名，fnOS 传进来的容器名带前导斜杠（报错里的 `" /apphub"`），按名字清理匹配不到，于是残留容器占着名字，compose 再创建就报 `Conflict`。现在项目名固定，`upgrade_init` 还会按「容器名 / `/?` 前缀名 / 项目标签 / 同镜像」四重兜底清理。

发布一个新版本的两种做法：

```bash
# A. 手动改版本号后打标签
#    编辑 manifest 的 version 与 app/docker/docker-compose.yaml 的 image tag
git commit -am "chore: bump 1.0.28"
git tag v1.0.28 && git push origin main --tags
```

```text
B. 在 Actions 页面选择 Build FPK → Run workflow → bump 选 patch
   （工作流会自动改 manifest / compose 版本号、打包、发 Release、更新 fnpack.json 并回写 main）
```

本地打包（需先安装 [fnpack](https://static2.fnnas.com/fnpack/fnpack-1.2.3-linux-amd64)）：

```bash
chmod +x fnpack-1.2.3-linux-amd64 && sudo mv fnpack-1.2.3-linux-amd64 /usr/local/bin/fnpack
fnpack build          # 仓库根目录执行，产出 apphub_<version>.fpk
```

单独更新源索引（一般由工作流调用，无需手工执行）：

```bash
python3 scripts/gen_fnpack.py --version 1.0.13 \
  --fpk apphub_1.0.13.fpk \
  --download-url https://github.com/TaroCats/FN-AppHub/releases/download/v1.0.13/apphub_1.0.13.fpk
```

> `fnpack.json` 中的 `sha256` 必须与 Release 上的 fpk 完全一致，否则 FnDepot 会校验失败并跳过该版本。请始终让工作流生成，不要手工编造哈希。

## 1.0.29 变更
- **分屏去掉间隔**：窗口之间不再留 8px 缝，紧贴铺满整个工作区。之前每格都有圆角和阴影，交界处会露出一条舞台底色，看着像画了很多个小卡片；现在分屏时窗口去圆角、去边框、去阴影，一条缝都没有。
- **拖交界处调整宽高**：分屏时把鼠标移到两个窗口的交界线上，光标会变成 `col-resize` / `row-resize`，拖动就能改变相邻两格的宽度或高度，悬停与拖动时显示一条高亮细线（不拖的时候完全不可见，不干扰画面）。只影响相邻两格，其它窗口保持不动。
- **尺寸按比例保存**：内部存的是比例而不是像素，所以调整完切到全屏再切回分屏、或者调整浏览器窗口大小，比例都保持不变；只有窗口数量变化导致行列结构改变时（比如从 3 个加到 4 个）才重置为均分。
- **单格最小尺寸保护**：宽度下限 220px、高度下限 160px（够放下标题栏和四个操作按钮），拖到极限会停住，不会把某一格压成点不到的窄条。
- **窄格自动收起 URL**：分屏把某一格拖得很窄时，标题栏会用容器查询自动隐藏地址、收紧按钮间距，保证图标、名称和操作按钮始终完整可用，不会换行或被裁切。
- **修复拖动中途卡住**：原来拖动过程中会重建分隔条元素，正在接收指针事件的那个元素被 `innerHTML` 清掉后指针捕获就丢了，事件随后落到 iframe 上被吞掉，表现为拖到一半不动。现在改为复用元素、只更新几何属性。
- **修复分隔条失效**：切换布局时清空了分隔条却没有清签名标记，再次进入分屏会因为"签名没变"跳过重建，导致分隔条完全不出现、无法拖动。

## 1.0.28 变更
- **镜像改为 CI 构建、设备端只拉取**：镜像由 GitHub Actions 用 `docker build-push-action` 构建后推送到 `ghcr.io/tarocats/apphub`（版本 tag + `latest`），compose 里删掉 `build:`，安装与升级不再在设备上现场 `docker build`。以前每次更新都要在 NAS 上重新构建一遍，既慢（首次还得拉 `python:3.12-slim`），又会在构建失败时把整个更新卡死——这是「经常更新报错」的主因。
- **根治 `pull access denied for apphub`**：旧 compose 写 `image: apphub:1.0.27` 且带 `build:`，docker 会先去仓库找一个叫 `apphub` 的镜像，找不到就报 `repository does not exist or may require 'docker login'`。现在镜像只来自 GHCR，不存在这个名字歧义；脚本也只在镜像名带 `/`（即远程仓库）时才执行 pull，不会再对本地构建镜像发起无意义的拉取。
- **根治 `container name "/apphub" is already in use`**：旧 compose 没有项目名，fnOS 传入的容器名带前导斜杠，按名字清理根本匹配不到，残留容器一直占着名字与 9080。现在 compose 增加 `name: apphub` 固定项目名，脚本按「容器名 → `/?` 前缀名过滤 → compose 项目标签 → 同镜像」四重兜底清理，并额外调一次 `compose down --remove-orphans` 收掉孤儿容器。
- **先拉后清，升级不会「拉到一半变砖」**：两个脚本都改为**先拉取新镜像、再清理旧容器**。反过来做的话，一旦拉取失败（网络抖动、镜像还没推上去），旧容器已被删除、新镜像又没有，应用直接下线。现在新镜像没到手就什么都不动。
- **拉取失败自动降级 `latest`**：指定版本 tag 拉不到时回退 `latest`，并把 compose 的 `image` 改写为 `latest`，避免 compose 因引用了不存在的版本 tag 而启动失败。
- **升级强制拉新**：`upgrade_init` 会先 `docker image rm` 本地同名 tag 再 `docker pull`，否则 docker 可能判定「已是最新」直接跳过，升级完跑的还是旧镜像。
- **CI 增加推送后校验**：镜像推送后用一个无凭据的 GHCR token 拉一次 manifest，确认能被匿名拉取。安装端不做 `docker login`，这一步能提前发现「包被设成私有」导致的装机失败。
- **卸载清理到镜像**：`uninstall_init` 除容器与 compose 项目外，一并删除 `ghcr.io/tarocats/apphub:*` 与历史遗留的 `apphub:*` 本地镜像，卸载后不残留占空间。
- **脚本兼容性修正**：改写 compose 时不再用 `sed -i`（busybox 版不支持无参数形式），改为「临时文件 + mv」，避免在部分 fnOS 环境下静默失败。

## 1.0.27 变更
- **内嵌浏览支持多窗口**：原来点卡片只能开一个内嵌页、开第二个就替换掉第一个。现在内嵌是一个工作区，可以同时开多个应用窗口，顶部标签栏按打开顺序排列，点标签切换、点标签上的 × 只关那一个窗口；已打开的应用在新建窗口的选择器里标记「已打开」，再选它就直接切过去，不会重复开。
- **三种布局：默认全屏、分屏、缩小**。全屏是当前窗口占满画面（默认，沿用旧行为）；分屏把所有窗口平铺，2 个左右各半、3 个左二右一、4 个 2×2，更多按列均分；缩小把窗口变成浮动窗，可拖标题栏移动、拖右下角改大小、点哪个哪个提到最前，双击标题栏回到全屏。
- **布局记忆与自适应**：布局选择存 `localStorage`，下次进来沿用；分屏按可用宽度自动降列（每列不少于约 260px），窄窗口和手机上不会把窗口挤成一条缝；窗口尺寸在窗口 resize / 进出浏览器全屏后重算。
- **单窗口容错独立**：每个窗口有独立的加载超时与探活，某个应用加载慢或拒绝内嵌时只在该窗口内提示，并给「新窗口打开」，不再影响其它已经正常显示的窗口。
- **窗口标题栏操作**：刷新、该窗口全屏、在新窗口打开、关闭，都在各自窗口上完成，不用先切到某个全局工具条。
- **快捷键**：`Alt+T` 打开新窗口选择器，`Alt+1..9` 切到第 N 个标签，`Esc` 关选择器 / 单窗口时退出工作区。没有用 `Ctrl/Cmd+T`、`Ctrl/Cmd+数字`——那是浏览器自己的快捷键，页面会被抢先拦截。
- **修复拖动失效**：浮动窗拖动时指针会滑进 iframe，`pointermove` 被 iframe 吞掉导致窗口不跟手。现在拖动/缩放期间临时屏蔽 iframe 的指针事件并加指针捕获，同时监听 pointer 与 mouse 两套事件兜底。
- **修复叠放不置顶**：浮动模式下点击被遮挡的窗口，原来只换标签不高亮层级，看起来像"点了没反应"。现在激活窗口独立抬升 z-index，点击即置顶。
- **`Esc` 不再误伤**：多窗口时按 `Esc` 不再一次性关掉全部窗口（1.0.26 之前是单窗口，直接关掉没问题）；只剩一个窗口时才退出工作区，否则提示用「关闭全部」。

## 1.0.26 变更
- **修复升级时旧容器清理不掉**：`upgrade_init` 里直接 `docker rm` 一个仍在运行的容器会失败——`container is running: stop the container before removing or force remove`，于是旧容器继续占着 9080 和应用名，随后 `docker compose` 创建新容器时报 `Conflict. The container name "/apphub" is already in use` 或端口被占用，升级卡在半路。现在改为「`docker stop -t 20` → 轮询确认真正退出（最长 30 秒）→ 仍未退出则 `docker kill` → `docker rm`，最后兜底 `rm -f`」，先停后删，升级过程不再依赖运行状态。
- **补全残留清理**：除按容器名清理外，再按 compose 项目标签（`com.docker.compose.project`）与同名镜像兜底清理，容器被改过名、存在多副本或历史残留时也能一并清掉。
- **等待端口释放**：删除完成后轮询 9080 是否真正空闲（最多 15 秒），避免新容器启动瞬间抢不到端口。
- **`install_init` 同一问题一并修复**：安装前的残留清理走同一套 stop → 等待 → rm 逻辑。
- **`uninstall_init` 不再空转**：原先直接 `exit 0`，卸载后容器仍留在系统里继续占用端口，现在卸载时先停后删。

## 1.0.25 变更
- **版本号可见**：新增 `GET /api/version`，版本号由 CI 写入镜像内 `VERSION` 文件，前端启动时读取——浏览器 / fnOS 应用窗口的标题会显示 `AppHub v1.0.25 · 应用聚合中心`，页面左上角品牌旁也会出现同款版本徽标，一眼就能确认装的是哪一版。
- **修复同端口不同主页地址被误判重复**：1.0.24 已按「IP + 端口 + 主页地址」判重，但线上若仍是 1.0.23，新增 `5666 + /Music` 这类同端口不同入口的应用会被旧逻辑（只比 URL，auto 模式下 URL 都是 `http://IP:5666`）直接拦成「该地址已存在」。1.0.25 起判重统一走三维比较，同一端口可以分别收录 `/`、`/Music`、`/app/dpanel/dpanel/ui` 等不同入口。
- **统一配置应用按统一 IP 判重**：auto 模式的主机最终都会被「访问地址」拉齐成同一个 IP，因此判重时直接用统一配置 IP 比较。同一台机器从 LAN（`10.x`）与 Tailscale（`100.x`）两个地址访问面板，也不会把同一入口重复收录成两个应用。
- **冲突提示带上具体地址**：重复时提示 `该地址已存在：DPanel（http://IP:5666/app/dpanel/dpanel/ui）`，直接给出被占用的完整地址，不用再去列表里翻是哪一条。

## 1.0.24 变更
- **重复判定加上主页地址**：新增与编辑应用时，原来只看「IP + 端口」，同一个 IP 端口下挂 `/`、`/admin`、`/jellyfin` 这类不同入口会被误判成重复。现在改为「IP、端口、主页地址」三者完全一致才算重复，同端口不同主页地址可以分别收录。
- **主页地址为空等同 `/`**：留空、只填 `/`、填 `admin` 或 `/admin/` 都会被归一化后比较，`/admin` 与 `admin/` 视为同一个主页地址，避免同一入口因写法差异被重复添加。
- **自定义地址自带路径也参与判定**：自定义模式下写成 `http://IP:端口/admin` 时，路径部分同样算作主页地址，与「端口 + 主页地址 /admin」的统一配置应用视为重复。
- **编辑也会拦截冲突**：改端口或改主页地址时若撞上已有应用，同样返回 409 并提示被哪个应用占用（自身不参与比较，不会把自己判成重复）。

## 1.0.23 变更
- **彻底移除 nginx**：容器不再安装 nginx，`start.sh` 直接 `exec uvicorn` 监听对外端口 9080，不再有 9080 → 127.0.0.1:19080 的中间转发层。删除 `app/webconf.py` 与全部 `webconf.apply()` 调用，端口、进程、日志都只对应一个服务，排查问题不再需要跨两层看。
- **移除调试面板与入口**：顶部「调试」按钮、右侧调试抽屉（应用上游/内嵌地址对照、日志流、级别过滤）以及配套的前端定时器与样式全部删除；后端 `GET/POST /api/debug` 一并下线，只保留 `/api/logs` 供排查时按需取日志。
- **修复编辑窗口打不开**：`openModal()` 里对不存在的 `form.mode` 赋值会抛 `TypeError`，异常发生在弹窗显示之前，所以点「编辑」毫无反应。改为把 `mode` 作为保存字段提交；表单控件统一用 `form.elements.xxx` 取值，避开 `form.name` 与表单自身属性冲突。
- **内嵌浏览统一走 IP + 端口**：应用地址取自「统一配置」里的 IP（默认当前访问 fnOS 的 host），即 `http://<IP>:<端口>`，一键切换网段只改这一个值，内嵌页与「新窗口打开」完全一致。
- **统一地址只认 IPv4**：保存、上报、批量重写三处都加校验，从域名（如 `office.app.5ddd.com`）访问面板时不会再把这个域名写成统一地址，历史遗留的域名值会被忽略并回退到当前 IP，避免应用地址被带回域名。

## 1.0.22 变更
- **彻底弃用域名方案：应用一律 IP 直连**。此前内嵌依赖 `app-<id>.fnos.local` 子域（内置 mDNS 应答）与 `/p/{id}/` 同源反代，两者都存在解析与改写上的脆弱点：客户端没配 hosts 就打不开、DNS 被代理或隧道接管时 `.local` 解析被拖慢数秒、路径前缀反代遇到绝对路径资源与前端路由容易错位。本版直接删掉整条链路，应用地址保存为 `http://<局域网IP>:端口`，浏览器按 IP 直连加载。
- **移除 mDNS 响应器与内置 hosts 写入**：删除 `app/mdns.py`，不再绑定 5353、不再向容器 `/etc/hosts` 写入 `app-<id>.<域名>` 映射，也不再提供 `/api/mdns/*`、`/api/hosts`、`/api/subdomains` 接口。局域网里不再有任何由 AppHub 发起的域名解析行为。
- **移除 `/p/{id}/` 同源反代**：删除 `app/proxy.py` 与 `SubdomainDispatcher`，不再改写上游 HTML、不再剥离 `X-Frame-Options`、不再注入运行时补丁。现在内嵌页就是应用本身，登录态、WebSocket、绝对路径与前端路由全部由应用自己负责，行为与直接用浏览器打开一致。
- **nginx 只托管面板**：容器内 nginx 依然对外监听 9080、把请求转给内部 `127.0.0.1:19080`，但不再生成任何按 `Host` 分流的虚拟主机；nginx 不可用时仍自动回退到 uvicorn 直连。
- **「访问地址」改为 IP 重写语义**：顶部仍只有一个访问地址入口，保存后把统一配置模式的应用地址批量重写成 `http://该IP:端口`；换网段只改这一个值，不用逐个编辑应用。
- **自动探测局域网 IP 更可靠**：删除对 Linux `ioctl` 的硬依赖，改为「ioctl → macOS `ifconfig` 解析 → 默认路由探测」三级回退，并按 `192.168 > 10 > 172 > 100` 打分挑选，避免 Clash/Tailscale 的 `198.18.x`、`100.x` 虚拟地址被当成访问地址。
- **前端精简**：去掉「内嵌/直连」模式切换、hosts 复制按钮、mDNS 自检面板与子域探活提示，浏览页只保留「新窗口打开」；编辑弹窗只填端口即可，主机位置显示当前访问 IP。
- **数据结构**：`mode` 字段保留但恒为 `direct`（兼容旧库，启动时统一迁移），`frame_path` 不再下发，历史 `proxy` 记录自动归为 `direct`。

## 1.0.20 变更
- **修复子域解析慢 / 偶发提示「子域解析失败」**：macOS 等客户端查询 `app-xx.fnos.local` 时会在同一个包里同时带 A 与 AAAA 两个问题。此前只对 A 作答、对 AAAA 返回空 NODATA，客户端不认这种裸否认，双栈解析要等到 2.5 秒超时才重传，代理跳转里再解析一次就累加到 5 秒，前端探活超时就会提示失败。现在按 RFC 6762 §6.1 对 AAAA 返回带 NSEC 的权威否定（type bitmap 只声明 A），解析从 2.28 秒降到 0.15 秒，本机缓存命中约 0.004 秒。
- **修复多问题查询里第二个问题被丢弃**：部分客户端对同包内第二个问题复用域名压缩指针（如 `c00c`），旧解析遇到指针直接放弃，AAAA 问题因此永远拿不到应答。现在正确跟随指针取名字与 `qtype/qclass`，并保留环路与越界保护。
- **同一次查询的应答合并为单个包**：A 与 NSEC 此前分两个包回，mDNSResponder 只接受第一个包、丢弃后续包，否定应答形同虚设。现在合并为单包（question 与 answer 一一对应），并统一用完整域名重编码 question 段，避免原包压缩指针在新包里的偏移失效。

## 1.0.18 变更

- **修复子域代理响应头重复**：上游（Kestrel / Jellyfin、Emby 一类应用）自带 `Server`、`Date` 响应头，代理原样透传后 uvicorn 又各写一份，一个响应里出现两个 `date`、两个 `server`。Safari（CFNetwork）遇到重复单值头会判定响应无法解析，直接显示「网页似乎有问题，或者可能已永久移动到新的 Web 地址」。现在 `date` / `server` 列入丢弃名单，并对所有响应头做同名去重（同名只保留第一条）。
- **修复子域模式相对跳转**：上游返回 `Location: web/index.html` 这类相对地址时，此前原样透传；现在按当前请求路径归一化为根相对地址（如 `/web/index.html`），避免不同客户端解析基准不一致导致跳到错误路径或空白页。

## 1.0.17 变更

- **mDNS 现在直接应答裸域名 `fnos.local`**：此前只匹配 `*.fnos.local` 子域，主面板地址仍靠 avahi 或系统 hosts；现在 `fnos.local` 本身与所有子域由同一个响应器应答，映射 IP 以「访问地址」里保存的值为准。
- **修复「映射了 IP 但解析不到」**：`alias_ip()` 改为严格校验，只有合法 IPv4（排除回环/未指定/组播）才用于应答；填了域名、IPv6、`127.0.0.1` 等非法值时自动回退到探测到的局域网 IP 并在日志告警（旧逻辑把非法值直接交给 `inet_aton`，抛错后整个应答被吞掉，表现为「查询无应答」）。
- **修复多 question 查询包的应答结构**：一个查询包里同时带 A 与 AAAA（macOS / 部分路由器常见）时，应答包的 question 段只保留当前这一条，避免 `qdcount=1` 与内容不符导致整包被客户端丢弃。
- **AAAA 查询回 NODATA**：本服务只有 IPv4，对 AAAA 显式返回 NOERROR + 0 条记录，客户端不必等 IPv6 超时。
- **主动通告**：服务启动、以及「访问地址」映射 IP 变更时，向 `224.0.0.251` 组播通告一次 A 记录，客户端不用等旧记录 TTL（30 秒）过期。
- **新增 mDNS 诊断接口**：`GET /api/mdns/status`（后缀列表、应答 IP 及来源、网卡、命中数）、`GET /api/mdns/selftest`（对 `fnos.local` 与各子域真实发起查询，对比「是否应答」与「实际解析到的 IP」）、`POST /api/mdns/announce`（手动重新通告）；调试抽屉新增「mDNS 自检」按钮并展示结果。
- **hosts 片段同时给出裸域名与子域**：`IP	fnos.local` 与 `IP	app-12.fnos.local` 一起复制，不认 mDNS 的设备一次贴全。

## 内嵌浏览的实现要点

- 只有一条路径：**IP 直连**。应用地址保存为 `http://<局域网IP>:端口`，内嵌 iframe 与新标签页用的是同一个地址，AppHub 不在中间做任何转发或改写。
- 因此不存在「代理层与上游争夺响应头」「绝对路径请求落到 AppHub 根」「Cookie/域名不一致」这类问题，应用怎么运行，在这里就怎么运行。
- 页面互相隔离：每个应用都是独立源，登录态由应用自己维护，AppHub 不读取也不代理应用的 Cookie。
- 少数站点设置了 `X-Frame-Options: DENY` 或 CSP `frame-ancestors`，浏览器会拒绝把它放进 iframe。这类应用请用工具条上的「新窗口」在标签页打开——这属于站点自身策略，不做绕过。
- 换网段或 NAS 改了 IP 时，在顶部「访问地址」里改一次 IP 即可，统一配置模式的应用地址会批量重写。

### 多窗口与三种布局

内嵌浏览是一个工作区，可以同时开多个应用窗口，顶部标签栏按打开顺序排列，关闭标签只是移除那一个窗口，不影响其它应用。

| 布局 | 行为 | 适用 |
| --- | --- | --- |
| 全屏（默认） | 当前窗口占满整个画面，其余窗口隐藏，用顶部标签切换 | 单应用专心操作，或手机竖屏 |
| 分屏 | 所有窗口紧贴平铺、**零间隔**：2 个左右各半，3 个左二右一，4 个 2×2，更多按列均分；拖交界处可自由调整宽高 | 边看监控边操作、对照两个应用 |
| 缩小 | 窗口变成浮动窗，拖标题栏移动、拖右下角改大小、点任意一个提到最前，双击标题栏回到全屏 | 让出背景看主应用，小窗盯状态 |

- 布局选择记在 `localStorage`（`apphub.ws.layout`），下次进来沿用它；缩小模式的窗口位置与尺寸在本次会话内保留。
- **分屏零间隔**：窗口之间不再留缝，直接铺满整个工作区，交界处不会露出底色。
- **拖交界处调整宽高**：分屏时鼠标移到窗口交界处会出现 `col-resize` / `row-resize` 光标，拖动即可改变相邻两格的宽度或高度；只影响相邻两格，其余窗口不动。悬停/拖动时显示一条高亮细线。单格有最小尺寸保护（宽 220px、高 160px，够容纳标题栏和操作按钮），拖到极限会停住而不是压成一条缝。
- **尺寸会被记住**：调好比例后切到全屏再切回分屏，比例保持不变；只有窗口数量变化导致行列结构改变时才重置为均分。
- 分屏的列数会随可用宽度自动降列（每列不少于 220px），窄窗口或手机上不会把窗口挤成一条缝。
- 打开窗口用右上角 `+`，或 `Alt+T`；`Alt+1..9` 直接切到第 N 个标签；`Esc` 关闭选择器，单窗口时再按一次退出工作区。
- 每个窗口标题栏自带刷新、该窗口全屏、在新窗口打开、关闭四个操作；窗口自己加载慢或被站点拒绝内嵌时，会在该窗口内单独提示，不影响其它窗口。
- 这里不再有 `Ctrl/Cmd+T`、`Ctrl/Cmd+1..9`：那是浏览器自己的新建标签与切标签快捷键，页面拿不到，会被浏览器先拦下，所以改用 `Alt` 组合。

## 非应用中心方式运行（调试用）

```bash
cd app/docker
docker compose up -d --build
# 浏览器访问 http://<NAS地址>:9080/
```

## 注意事项

- 容器使用 `network_mode: host`，容器内可直接探测 `127.0.0.1:<port>`，因此扫描结果与宿主端口一致；这也意味着 9080 必须是空闲端口。
- 只读挂载 `docker.sock`，应用仅做 `docker ps` 类查询，不会启停你的容器。
- 数据库为单文件 SQLite，备份 `apphub.db` 即备份全部访问列表。
- 应用本身无账号体系，依赖飞牛应用中心入口的访问控制；如需外网访问请在飞牛「远程访问/反向代理」侧加认证。
